# Trias · 三权分立的 AI 开发流水线（设计文档）

## Fable 5.1 出方案 · GPT 执行 · Opus 验收 · 脚本衔接 · 值守兜底 · 邮件通知

> **用途**：拿给任何人，他都能照着搭一套，或者按自己情况换掉其中任何一块。
> **来源**：这套做法在一个真实项目上无人值守跑完了多个子阶段，含返工、两线并行和通宵值守。本文是把跑过的那套抽象、瘦身后的版本。附带的脚本已用假模型端到端跑通（14 个场景：开发、返工四级、程序结果没过改判、服务故障、冒烟偶发、等手册、值守、审稿包、读大文件拦截、一行安装等）。踩过的坑在第 14 节单列。
> **仓库**：https://github.com/wyatttml/trias 。本文件在 `docs/` 下，仓库根即复刻包；`install.sh` 一行接入，默认只装核心，`--full` 装全套。第 17 节是一小时搭起来的清单。

## 0. 一页看懂

```
AI 产品经理（只做业务判断，不碰终端）
   │ 对话                                        ▲ 邮件 / 弹窗（通过、返工、需决定、完成）
   ▼                                             │
Fable 5.1 —— 方案模型：写手册；返工第 4 级、审稿包里出场
   │ 产出：每段手册 Sn_*.md、项目状态.md
   ▼                                             │
┌──────────── run.sh 编排脚本（无人值守循环）──────────────────────────┐
│ 读 项目状态.md → 当前子阶段是什么状态？（没手册就等手册）              │
│ 未开始 / 返工中 ──► Codex（GPT）照手册开发 ──► 自己改成「待验收」      │
│ 待验收 ──► checks.sh 程序检查（全量测试 / 冒烟三中取二 / 密钥扫描）    │
│         ──► tally.py 计数定级（服务故障？偶发？第几次失败？）          │
│         ──► Opus 验收：先分诊，和上一版并排看 ──► 结论三选一           │
│ 通过   ──► 程序结果没过就改判返工；过了，遗留项追加进下一段手册        │
│ 返工   ──► 按级别：执行模型修 / 先出检查单 / Opus 亲修 / 交方案模型    │
│ 需决定 ──► 弹窗 + 邮件等人；10 分钟没人答且不涉红线 → 按推荐办         │
└─────────────────────────────────────────────────────────────────────┘
      ▲ 可选：duty.sh 值守（不用 AI，常驻）：出事起短会话处理、返工单先起草、夜里照草稿办
```

五条核心思想，比任何脚本细节都重要：

1. **三个模型各干一件事，用文件交接，不用聊天交接。** 手册是方案模型给执行模型的合同；验收结论是验收模型给执行模型的返工单；进度表是所有人共用的唯一事实。模型之间也不互发消息，审稿走审稿包文件。
2. **脚本是唯一的状态推进者。** 执行模型只被允许做一个状态变化：把自己的段改成「待验收」。其余全由脚本和验收员改。
3. **程序说了算。** 测试、冒烟、密钥扫描由脚本跑出结果；验收模型只读结果、和上一版成品并排看 2 到 3 件、下结论，15 次工具调用以内。程序结果没过，验收员写「通过」也会被脚本改判返工。
4. **先分诊再返工。** 只有程序行为错才返工；成品质量进「调优清单」由人或方案模型改提示词和模板；网络故障不算轮次，自动重跑；风格只提醒。
5. **人只在几类事上被打扰。** 新开付费服务或云资源、删数据、改范围、改密钥配置，以及返工用完、额度用完。其余 10 分钟没人答就自动按推荐办。

## 1. 为什么这样分工

| 角色 | 用什么 | 干什么 | 为什么是它 |
| --- | --- | --- | --- |
| 方案与裁决 | Fable 5.1（Claude） | 写每段手册；改流程；返工第 4 级裁决；审方案（审稿包） | 最强的模型，但额度最贵。只在对话和值守起的一次性短会话里用，不进主循环 |
| 执行 | GPT（Codex CLI，`codex exec`） | 照手册写代码、测试、冒烟脚本、交付说明；返工第 2 级写检查单 | 命令行可无人值守；沙箱档位可控；独立订阅，不耗 Claude 额度 |
| 验收 | Opus 5.5（Claude Code CLI，`claude -p --effort high`） | 读程序结果，并排看成品，下三选一结论；返工第 3 级亲修 | 与执行模型不同厂商，不会给自己放水；比 Fable 便宜，每段都跑得起 |
| 衔接 | bash + 几个小 Python | 状态机、起停模型、跑检查、计数定级、等人、通知 | 确定性、可复盘，出事看日志就能定位 |
| 值守（可选） | `duty.sh`，本身不用 AI | 出事、返工起草、夜里的决定、审稿包，都按需起一次性短会话 | 没人在时也能处理；不挂在任何对话上，不叫醒任何对话 |
| 通知 | Gmail SMTP（可选 webhook）+ Mac 弹窗 | 推到手机 | 零成本；手机装 Gmail 就能收推送 |
| 日常运维 | Opus（对话） | 流水线停了时按《停了怎么办》处理 | 日常问题不值得用 Fable 的额度 |

替换规则（第 16 节有替换表）：每一格都可以换，但保住两条：**执行与验收不是同一个模型**；**方案由你能用到的最强模型写**。

方案和手册还可以「双审」：方案模型审一份，再让执行模型只读审一份（`codex exec -s read-only`），各出一份审稿文件。不加代码，只是一个习惯：两家模型看同一份手册，漏掉的东西不一样。

## 2. 目录与文件约定

```
项目根/
├─ AGENTS.md                  执行模型每次开工自动读的项目规则（templates/AGENTS.md）
├─ CLAUDE.md                  方案、验收模型读的规则卡：角色、文件在哪、怎么判好坏、强度（templates/CLAUDE.md）
├─ 项目状态.md                唯一事实来源：进度表 + 决策台账（templates/项目状态.md）
├─ 手册/
│   └─ S1_xxx.md … Sn_xxx.md  每段一份，固定章节（templates/手册_Sn_子阶段名.md）；S1a、S1b 可共用一份 S1_xxx.md
├─ pipeline/
│   ├─ run.sh                 编排脚本
│   ├─ checks.sh              程序检查（按项目改的唯一文件）
│   ├─ tally.py               冒烟三中取二、计数定级、服务故障、偶发放行
│   ├─ state.py               读写进度表
│   ├─ notify.py              邮件 / webhook / 弹窗
│   ├─ run_sh_check.py        改 run.sh 后、重启前的检查
│   ├─ duty.sh                值守（可选）
│   ├─ prompts/               dev_start  dev_rework  accept  check  fix（核心）；duty_incident  duty_decide  review_planner  review_reviser（可选）
│   └─ 停了怎么办.md           给运维模型看（templates/停了怎么办.md）
├─ 审稿包_XX.md               可选：要方案模型审的东西（templates/审稿包模板.md）
├─ .claude/                   可选：hooks/bigread_guard.py、agents/sample-viewer.md、agents/log-digger.md
├─ scripts/smoke_Sn.py        每段一个真实冒烟脚本（执行模型写）
├─ 验收证据/Sn/               交付说明.md（执行模型写）  验收结论.md（验收模型写）  检查单_第N轮.md
├─ 运行数据/pipeline/         不进 Git：日志/、accept_Sn.json、fail_counts_Sn.json、等待决定.md、停止、run.pid、dev.pid、值守模式
└─ .env                       不进 Git：GMAIL_* 等
```

命名规则：子阶段编号 `S1、S2…`，可带小写后缀 `S2a、S2b`（前缀可用环境变量 `STAGE_PREFIX` 改）；手册文件名必须以 `S1_` 这样的前缀开头，脚本靠前缀找手册；文件名带「审稿」「审阅」的不算手册。

## 3. 状态机

```
（等手册）──► 未开始 ──► 开发中 ──► 待验收 ──┬──► 已通过（或 已通过·待 AI 产品经理亲验）
                          ▲                 ├──► 待验收（服务故障，原样重跑，不计轮次）
                          │                 ├──► 返工中 ──► 开发中（按级别，上限 4 轮）
                          │                 └──► 等待决定 ──► 继续 / 通过 / 返工：xxx
                          └──────────────────────────────────┘
```

| 状态 | 谁改 | 脚本接着做什么 |
| --- | --- | --- |
| 未开始 | 脚本改成「开发中」 | 手册不在就等手册；在就渲染 dev_start，起执行模型 |
| 开发中 | 执行模型改成「待验收」（没改则脚本代改） | 脚本代提交 Git |
| 待验收 | — | 旧结果挪开 → checks.sh → tally.py → 服务故障就等着重跑，否则起验收模型 |
| 返工中 | 脚本 | 按 `escalation_level` 选 dev_rework / 先 check 再 dev_rework / fix / 等方案模型 |
| 已通过 | 脚本 | 遗留项追加到下一段手册（没手册先暂存），发邮件，进入下一段 |
| 已通过·待 AI 产品经理亲验 | 脚本（`MANUAL_REVIEW_STAGES` 列出的段） | 同上；提醒人去亲自验 |

进度表格式（`state.py` 只认这一种）：

```
| S1 第一段名称 | 未开始 | |
```

## 4. 手册 = 合同（方案模型的产出）

每段一份，方案模型在开工前写好。固定章节（模板在 `templates/手册_Sn_子阶段名.md`）：目标 / 范围（要做·不做）/ 现状 / 设计 / 开发步骤 / 测试清单 / 真实冒烟 / AI 产品经理验收步骤 / 降级路径 / 通过线 / 开工核对 / 实现记录。

四条铁律：

1. **通过线只有两条。** 程序确定项全过（测试、冒烟、密钥扫描和你在 checks.sh 里加的项）；成品和上一版并排看不退步。不设数字指标，命中率、耗时、页数的升降只当观察。
2. **手册与代码不一致，以代码为准。** 执行模型在「开工核对」记一行，继续干，不停下来问。
3. **手册会生长。** 验收通过时脚本把结论里「遗留到下一阶段」自动追加到下一段手册末尾；下一段还没手册就先存 `运行数据/pipeline/遗留_待并入_<段>.md`，写手册的人并进去。
4. **段内冻结。** 一段开工后不再给它加新检查或通过条件；返工单只能依据开工时手册已有的「要做」。新想到的检查写进下一段。

写手册时最有用的几条全局规则：

- 不搞任何形式的自审仪式：不开审核子代理、不写自审报告、不做签署回执。
- 不写一次性脚本；每段只有一个冒烟脚本，重跑就覆盖。冒烟结果每步记 `status` 和 `error`（错误原文），流水线靠它认出超时、429 这类服务故障。
- 同一问题修两次还不过：走降级路径；没有降级路径就写进交付说明「需 AI 产品经理决定」，正常收尾。
- 只有会改变费用、范围、安全、隐私的事才问人，一次不超过 5 个，每个附推荐。

## 5. 一个子阶段的完整一圈

1. 脚本读进度表，拿到第一个未通过的段（如 S2）及其状态。手册还没写好就等着，写好了自己接着跑。
2. 状态「未开始」：改成「开发中」，用 `prompts/dev_start.md` 渲染提示词，`codex exec` 起执行模型，提示词从 stdin 喂入，输出全进日志。
3. 执行模型照手册开发、写测试（只跑相关的）、写 `scripts/smoke_S2.py`、填「实现记录」、写交付说明、把状态改成「待验收」、退出。
4. 脚本代提交 Git（执行模型不碰 Git）。
5. 状态「待验收」：先把上一轮的结果文件挪开，再跑 `checks.sh S2`（全量测试、冒烟最多三次、密钥扫描、可选回归集），然后 `tally.py finish S2` 合并出 `passed`、`failed_items`、`escalation_level`、`service_outage`、`flaky_allowed`。
6. 服务故障（测试和密钥都过、失败的冒烟步全是超时 / 429 / 5xx / 连不上）：不叫验收模型、不计轮次，等 10 分钟没人答就原样重跑。
7. 用 `prompts/accept.md` 渲染提示词，`claude -p` 起验收模型。它先分诊，再读手册、交付说明、accept 结果，和上一版并排看 2 到 3 件，写 `验收证据/S2/验收结论.md`，第一行三选一。
8. 分支：
   - **通过**：程序结果没过就改判返工；过了改状态、遗留项追加进 S3 手册、提交、发邮件。
   - **返工**：状态改「返工中」，下一圈按返工级别处理（第 8 节）。装了值守就先进「返工待定稿」（第 9 节）。
   - **需决定**：进入等人机制（第 6 节）。
9. 回到第 1 步。进度表全部通过时发邮件「流水线全部完成」，退出。

## 6. 等人机制（需决定）

**触发**：验收结论「需决定」；返工第 4 级；返工超上限；验收判通过但程序结果没过且轮数用完；模型连续两次异常退出；额度用完；程序检查没生成结果文件；进度表出现未知状态。

**三个渠道同时发**：
1. 写 `运行数据/pipeline/等待决定.md`：子阶段、原因、推荐、会自动还是一直等；最后一行留给人写决定。
2. 发邮件，标题「流水线停了，等你决定（S2）」，正文说清推荐和两种处理方法：点弹窗，或新开一个对话粘贴「流水线停了，按 pipeline/停了怎么办.md 处理」（这句可用 `HELP_LINE` 改）。
3. Mac 弹窗，两个按钮「按推荐办」「我自己看」。点「我自己看」会在决定文件里追加一行暂停，之后不再自动按推荐。Linux 没有 osascript 自动跳过，只靠邮件和决定文件。

**节奏**：5 分钟后再提醒一次（邮件 + 弹窗）。**10 分钟没人答且允许自动的，按推荐办**，并发邮件告知「已自动按推荐办」。

**永远等人的几类**：新开付费服务或云资源、删数据、改范围、改 .env（验收模型写「可自动按推荐：否」）；返工第 4 级、返工用完、额度用完、程序检查连续两次没出结果（脚本自己判）。

**人的回复只有四种**，写在决定文件最后一行，脚本 30 秒内接着跑：

| 写什么 | 效果 |
| --- | --- |
| `按推荐` | 执行文件里写的推荐 |
| `继续` | 返工计数清零，按当前状态继续（服务故障那种不清零） |
| `通过` | 判该段通过，遗留项照常追加 |
| `返工：要改什么` | 这句话作为返工单交给执行模型 |

**防骚扰规则**（都来自真实事故）：
- 同一原因连续出现第二次就一直等人，不再反复弹窗。
- 推荐文本不可机械执行时（如「通过（前提是……）」）不静默死循环，发邮件说明并继续等。
- 额度用完不自动继续：认出 `QUOTA_PATTERN` 的字样就一直等，免得一遍遍白跑。
- 不懂技术的人回「按推荐」的比例极高。所以推荐一定要写成可执行的指令词开头：`通过` / `继续` / `返工：…`。

## 7. 通知设计

| 事件 | 标题 | 正文要点 | 要人操作吗 |
| --- | --- | --- | --- |
| 验收通过 | S2 xxx 验收通过 | 验收员的一句话摘要；有调优清单就加一句「有 N 条要改提示词 / 模板」 | 否 |
| 判返工 | S2 xxx 判返工（第 1 次验收） | 摘要；「会自动返工，不用你操作」；同样带调优清单提醒 | 否 |
| 需决定 | 流水线停了，等你决定（S2） | 原因、推荐、会不会自动、两种处理方法 | 是 |
| 再提醒 | 再提醒一次：流水线在等你（S2） | 推荐、决定文件路径 | 是 |
| 自动按推荐 | 已自动按推荐办（S2） | 推荐了什么 | 否 |
| 按推荐失败 | 按推荐办失败（S2） | 推荐不可执行，请直接写决定 | 是 |
| 等手册 | S3 等手册 | 手册写好后自己接着跑；上一段遗留暂存在哪 | 是 |
| 异常退出 | 流水线异常退出 | 退出码、最后一条命令、怎么处理 | 是 |
| 全部完成 | 流水线全部完成 | 等你总验 | 是 |

写法原则：第一句就是结论；正文明确「要不要你做什么」；不带日志、不带密钥、不带命令输出；标题带子阶段编号，手机上扫一眼就知道进度。

发邮件的同时，macOS 上弹一个只有「知道了」的窗口，30 分钟自动消失；脚本自己弹带按钮窗口的那两类不重复弹。`.env` 写 `NOTIFY_POPUP=0` 关掉。

**Gmail 配置（一次性，5 分钟）**：
1. Google 账号 → 安全 → 开两步验证。
2. 搜「应用专用密码」→ 新建一个 → 得到 16 位密码。
3. 项目根 `.env` 写 `GMAIL_USER`、`GMAIL_APP_PASSWORD`、`NOTIFY_EMAIL`（样例在 `templates/.env.example`），确认 `.gitignore` 含 `.env`。
4. 测一下：`python3 pipeline/notify.py 测试 正文`，看 `运行数据/pipeline/日志/notify.log` 里是不是 `mail:ok`。

走 587 端口 STARTTLS，465 常被本机代理挡住。缺配置时脚本静默只记日志，不会把流水线搞死。

**换渠道**：`.env` 加 `NOTIFY_WEBHOOK` 和 `NOTIFY_WEBHOOK_KIND=slack|feishu|wecom`，群机器人就能收；几个渠道可以同时开。

## 8. 返工四级与分诊

**先分诊。** 验收模型对每个问题先标一层，只有第一层走返工：

| 层 | 例子 | 怎么处理 |
| --- | --- | --- |
| 程序行为错 | 该做没做、做错、崩溃、底线没拦住、比上一版退步 | 进「问题清单」，判返工，走下面四级 |
| 成品质量 | 提示词写得平庸、模板不好看、素材不对、文案啰嗦 | 进「调优清单」，人或方案模型直接改，改在最宽的一层；不归执行模型、不走四级 |
| 网络 / 环境 | 超时、429、5xx、连不上 | 不计轮次，原样重跑（多数时候脚本已自己处理，不会叫到验收模型） |
| 风格 | 配色、字体、版式、标题长短 | 只提醒，写进遗留，不阻塞 |

为什么要分：执行模型拿到「成品写得不好」的返工单，会往提示词里堆禁令补丁、加风格拦截，成品没变好，流程越来越长。

**再定级。** `tally.py` 把每项（全量测试 `tests`、冒烟某步 `smoke:<步>`、回归某件 `regress:<件>`、密钥 `secrets`）的真失败次数累计在 `fail_counts_<段>.json`（只加不清），当前没过的项里次数最多的就是 `escalation_level`：

| 级别 | 谁修 | 提示词 | 为什么 |
| --- | --- | --- | --- |
| 1 | 执行模型 | `dev_rework.md`（带验收结论或返工单原文） | 大部分问题一次就修好 |
| 2 | 执行模型，但先开一个只读会话写检查单 | `check.md` → `验收证据/<段>/检查单_第N轮.md` → `dev_rework.md` | 修了还不过，多半是没找到根子；换一个干净的会话专门找 |
| 3 | 验收模型亲修，只修这一项 | `fix.md` | 执行模型两次没修好，换一家模型来修 |
| 4 | 方案模型 | 停下等：改手册后写「返工：…」，或判「通过」 | 三家都没修好，多半是手册本身有问题 |

每级修完都照常全验，三中取二不省。返工上限 `MAX_REWORK` 默认 4 轮，用完仍不过就停下等人。

**几条配套规则：**
- 程序结果没过（`passed` 不是 true）不得判通过。验收员写了「通过」，脚本改判返工并写一份返工单「修到 failed_items 全过」。
- 返工单只许本段范围：每条要指到本段手册「要做」的条目，或本段引入的退步；指不到的进遗留。
- 冒烟三中取二：第一次就过的步算过；没过的步（不超过 `SMOKE_RETRY_STEPS`，默认 2 步）再跑两次，两次都过算过，记 `flaky_steps`；否则算真失败。一轮没过的步太多就不重跑，直接全算真失败。
- 偶发放行：回归某件上一批过、本批首次坏、其余全过，记 `flaky_allowed`、算过，写进下一段必修；连续两批坏才修。前缀由 `FLAKY_PREFIXES` 定，设空就不放行。
- 返工的验证按「改动波及面」跑：`dev_rework.md` 里有一张表（你改了哪里 → 还要补跑什么），各项目自己填。全量测试、整批冒烟交给流水线跑一次，执行模型不重复跑。

## 9. 值守（可选组件，`pipeline/duty.sh`）

不装它，核心流水线和单人用法一样跑。装了它，没人在时也能处理事情。

**它是什么**：一个常驻后台的 bash 脚本，本身不用 AI，不挂在任何对话上。每分钟看一次四件事，需要判断时起一个一次性短会话（`claude -p --effort high --permission-mode bypassPermissions`）：读文件、写结果、结束，不记得任何东西。

| 看什么 | 什么时候算 | 起谁 | 做什么 |
| --- | --- | --- | --- |
| 出事 | 日志出现「失败 / 卡住 / 退出码非 0」或 Traceback；或 `run.pid` 里的进程没了、又没有「停止」文件，连续 3 分钟 | 验收模型（`duty_incident.md`） | 照《停了怎么办》查原因，能恢复就恢复，结果发邮件。20 分钟内不重复起 |
| 判返工 | 决定文件带「返工待定稿」 | 级别 1 验收模型，级别 2 起方案模型（`duty_decide.md`） | 起草返工单。白天发给人看，10 分钟没回按草稿办，点「我自己看」就一直等；夜里直接办 |
| 夜里的「一直等」 | 值守模式为「睡觉」，决定文件写着「一直等你」 | 方案模型 | 能定的直接办并通知；付费、删数据、改范围、改 .env 留给人。第 4 级返工夜里由它改手册、提交后写「返工：…」 |
| 审稿包 | 值守模式为「睡觉」，项目根有 `审稿包_*.md` | 按状态行轮流起两个模型 | 第 10 节 |

**怎么和 run.sh 配合**：run.sh 判返工时看 `duty.pid` 活不活。活着，就把决定文件写成「返工待定稿」，不弹窗、不发「等你决定」，交给值守；不活，就和没装值守一样，结论直接喂回执行模型。run.sh 正常退出（停止、全部完成）会删掉 `run.pid`，所以值守看到「文件在、进程没了」就知道是异常退出或被杀。

**值守模式**：`运行数据/pipeline/值守模式` 只有「日常」「睡觉」两种。人说去睡觉就只改这一个文件，不起停任何脚本。

**保险**：每份决定文件只起草一次；短会话写不出能用的决定（不是 `继续` / `通过` / `返工：…`），就不自动办、通知人；白天要先改手册的，不自动办；所有动作记在 `运行数据/pipeline/值守记录.md`。

**测试开关**：`DUTY_ONCE=1`（只扫一轮）、`DUTY_FAKE=1`（不调模型，草稿取 `DUTY_FAKE_DRAFT`）、`DUTY_NOTIFY`（通知命令）、`DUTY_DIALOG=off`、`DUTY_AUTO`（白天自动按草稿的秒数）、`DUTY_LOG_FROM`、`DUTY_FAKE_REVIEW`。`tests/e2e.sh` 场景十、十一就是这样跑的。

## 10. 审稿包（可选组件）与读大文件拦截

**审稿包**解决的是「两个模型怎么商量」：方案要方案模型审时，不让它们互发消息，而是由验收模型（日常执行者）维护一份 `审稿包_XX.md`，方案模型把意见写进 `审稿包_XX_回复.md`。审稿包顶部一行状态驱动，最多 2 轮：

| 状态 | 谁做 | 做完改成 |
| --- | --- | --- |
| `状态：待方案模型审第 1 轮` | 方案模型审全文和材料，意见编号写进回复文件 | `状态：待验收模型处理第 1 轮` |
| `状态：待验收模型处理第 1 轮` | 验收模型一次处理完全部意见，第六节逐条记「采纳 / 不采纳」 | `状态：待方案模型审第 2 轮` |
| `状态：待方案模型审第 2 轮` | 方案模型只看变更记录，有分歧直接敲定 | `状态：已定` |

白天人在两个窗口各贴一句短话串起来；夜里值守串。保险：同一状态只起一次；短会话跑完状态没变就记失败、通知、不重试；每包最多 3 个短会话。状态行一定是最后一步改，值守只认状态行。模板六节：审什么、已定不许翻、材料清单、要回答的问题、验收模型的判断（给方案模型当靶子）、变更记录。

**读大文件拦截**（`bigread_guard.py`，Claude Code 的 PreToolUse 钩子）：主对话读图片、PDF、超 200 KB 的文件直接拒绝，提示交只读子代理（`sample-viewer` 看成品、`log-digger` 翻日志），主对话只收结论。大段原文一进主对话就一直占着上下文，后面每一轮都要为它付费。子代理和无人值守会话不拦；任何异常一律放行，绝不卡住对话。参数（大小阈值、媒体扩展名、读命令）在文件顶部。

## 11. 提示词（索引与写法经验）

全文在 `pipeline/prompts/`，这里只列每份管什么和关键约定。

| 文件 | 谁读 | 管什么 |
| --- | --- | --- |
| `dev_start.md` | 执行模型 | 开工：只做哪一段、先做上一段遗留、只跑相关测试、冒烟写法、只修程序行为、收尾顺序 |
| `dev_rework.md` | 执行模型 | 返工：带结论 / 返工单 / 检查单原文；不碰调优清单；按波及面表补跑 |
| `accept.md` | 验收模型 | 验收：先分诊、通过线两条、并排看、返工单只许本段、段内冻结、偶发与服务故障怎么写、结论格式 |
| `check.md` | 执行模型（只读会话） | 返工第 2 级：找根子，写检查单 |
| `fix.md` | 验收模型 | 返工第 3 级：只修这一项，修完跑全量 |
| `duty_incident.md`、`duty_decide.md` | 值守短会话 | 出事处理；起草决定 |
| `review_planner.md`、`review_reviser.md` | 值守短会话 | 审稿包两轮 |

渲染变量：`{STAGE}` `{NAME}` `{FILE}` `{ROUND}` `{SANDBOX_NOTE}` `{VERDICT}`（验收另有 `{MAX}`）。`{SANDBOX_NOTE}` 随 `CODEX_SANDBOX` 档位变：保守档告诉执行模型「沙箱里跑不了的写清楚即可」，全权限档告诉它「不许再拿沙箱当理由」。

验收结论的固定格式（脚本靠它分支）：

```
结论：通过 / 结论：返工 / 结论：需决定      ← 第一行只能是三者之一
## 问题清单          返工时每条：现象、复现方法、期望、对应手册哪一条
## 并排对比          每件：上一版 → 本次，退步 / 持平 / 更好
## 遗留到下一阶段     通过时脚本把这一节追加进下一段手册
## 需决定            倒数第二行「可自动按推荐：是/否」，最后一行「推荐决定：通过 / 继续 / 返工：…」
## 调优清单          成品质量问题，通知里会提醒条数
## 给 AI 产品经理的一句话摘要
```

写提示词的经验：
- 开头一句就定「只做哪一段、手册在哪」。
- 反复强调「无人值守，不要提问」，否则模型会停在半路等回答。
- 收尾动作写死顺序，最后一条永远是「把状态改为待验收，然后结束」。
- 把真实返工过的原因写进去，但写成规则，不写来由。
- 验收提示词限定工具调用次数、结论行数、第一行格式；三选一的判定规则写清楚，尤其是「程序结果没过不得判通过」和「红线永远需决定」。
- 提示词里的项目专有内容（波及面表、安全校验清单）留空格子让各项目自己填，不要把别的项目的经验硬塞进来。

## 12. 脚本（索引与关键片段）

| 文件 | 行数 | 管什么 |
| --- | --- | --- |
| `run.sh` | 353 | 状态机、起模型、等人、返工四级、接管 |
| `checks.sh` | 60 | 全量测试、冒烟最多三次、密钥扫描、回归集钩子；只写 `items` 和 `numbers` |
| `tally.py` | 165 | 三中取二、计数定级、服务故障、偶发放行；写回 `passed` 等 |
| `state.py` | 66 | 读写进度表 |
| `notify.py` | 109 | Gmail、webhook、弹窗 |
| `run_sh_check.py` | 69 | 语法、shellcheck、未赋值变量 |
| `duty.sh` | 251 | 值守（可选） |

`accept_<段>.json` 的样子（`checks.sh` 写前三个字段，`tally.py` 补后面的）：

```json
{"stage": "S2",
 "items": {"tests": "pass", "secrets": "pass", "smoke:登录": "pass", "smoke:导出": "fail"},
 "numbers": {"tests_exit": 0, "secret_hits": 0,
             "smoke": {"status": "FAIL", "runs": 3, "flaky_steps": [], "true_failed_steps": ["导出"]}},
 "passed": false, "failed_items": ["smoke:导出"], "escalation_level": 2,
 "service_outage": false, "flaky_allowed": []}
```

`run.sh` 返工中分支的骨架：

```bash
n=$(( $(rework_count "$stage") + 1 ))
lvl="$(jget "$acc" escalation_level)"
if { [ "$lvl" -ge 4 ] && [ ! -f "$v" ]; } || [ "$n" -gt "$MAX_REWORK" ]; then
  wait_decision "$stage" "…交方案模型…" "交方案模型定：…" 0     # 一直等
elif [ "$lvl" = 3 ]; then  render fix.md   → run_claude …        # 验收模型亲修
elif [ "$lvl" = 2 ]; then  render check.md → run_codex …          # 先出检查单，再走下面
fi
render dev_rework.md VERDICT_FILE="$v" → run_codex …
```

`run.sh` 通过分支的那道闸：

```bash
结论：通过)
  if [ "$(jget "$acc" passed)" != true ]; then      # 程序结果没过就不能通过
    log "验收员判通过，但程序结果没过，改判返工"
    … 写返工单，状态改「返工中」…
  fi
```

几处容易漏的细节：
- 脚本顶部 `trap 'exit_alarm $? "$BASH_COMMAND"' EXIT`：用 EXIT 而不是 ERR，因为 `set -u` 的「变量未赋值」不触发 ERR。
- 待验收开头先把旧的 `accept_<段>.json` 挪成 `_prev`：哪一步没写出来时，旧数据不能冒充本轮。
- `wait_decision` 有两个前缀变量：`DRAFT_GATE=1`（返工待定稿，交值守、不通知）、`KEEP_ROUNDS=1`（「继续」不清零轮数，服务故障用）。改 run.sh 前先跑 `run_sh_check.py`，它会把只在前缀里赋过值的变量当成未赋值抓出来。
- 子段找共用手册时去小写后缀用 `${1%%[[:lower:]]*}`，不要用 `[a-z]`：UTF-8 区域设置下 `[a-z]` 会匹配大写字母。

## 13. 运行与运维

**启动**（项目根）：

```bash
nohup caffeinate -dims bash pipeline/run.sh >> 运行数据/pipeline/日志/nohup.out 2>&1 &
nohup bash pipeline/duty.sh >> 运行数据/pipeline/日志/duty.log 2>&1 &     # 可选
```

Linux 去掉 `caffeinate -dims`（Mac 上它防止合盖休眠）。

**停止**：`touch 运行数据/pipeline/停止`。脚本在每个检查点看这个文件，正在跑的模型会做完当前段。**不要** `pkill` 模型进程，会误杀你自己正在用的 Codex 或 Claude 对话。

**重启**：改了 `run.sh` 或提示词要重启才生效。改了 run.sh 先跑 `python3 pipeline/run_sh_check.py`，最后一行「可以重启」才重启。挑空档（在等决定、在等手册、刚进新一段），不杀正在跑的执行模型、测试和验收。新进程按 `dev.pid` 等正在跑的执行模型做完再接手，接手后看它有没有正常收尾，没有就按当前状态重新开工。值守起的无人短会话检查过了可以自己重启；对话里的模型要先得到人同意。

**看哪里**：

| 想知道 | 看 |
| --- | --- |
| 现在停在哪、要我做什么 | `运行数据/pipeline/等待决定.md`（不存在 = 没在等人） |
| 流水线在干什么 | `tail -40 运行数据/pipeline/日志/pipeline.log` |
| 某段为什么返工、第几级 | `验收证据/Sn/验收结论.md`、`运行数据/pipeline/accept_Sn.json`、`fail_counts_Sn.json` |
| 执行模型干了什么 | `运行数据/pipeline/日志/Sn_dev_*.log`（最后回复在 `Sn_dev_last.txt`） |
| 值守做了什么 | `运行数据/pipeline/值守记录.md`、`日志/duty_*.log` |
| 邮件发出去没有 | `运行数据/pipeline/日志/notify.log` |

**运维分工**：流水线停了，先让便宜的模型（Opus）按 `停了怎么办.md` 处理；文件开头五条判定哪些情况必须换方案模型（改标准或手册、同一问题复发、删数据、问「为什么这样设计」）。

**给不懂技术的人的操作面**只有三样：看邮件；点弹窗的「按推荐办」；打开一个 .md 文件在最后一行写一个词。装了值守再加一样：去睡觉时改一个文件。

**省上下文**：执行期一个对话超过约 25 万 token，写交接文件（只写现状和下一步）换新对话；商量方案期不换，拖长就把讨论现状写进文件。成品和日志交只读子代理。对话里日常用中等强度，写手册、提示词、验收判定、改无人值守脚本时切高强度；脚本里的验收、亲修、值守一律 `--effort high`。

## 14. 踩过的坑（真实事故，已在脚本里修）

| # | 事故 | 原因 | 现在怎么防 |
| --- | --- | --- | --- |
| 1 | 弹窗失败、日志乱码、脚本静默退出 | bash 按字节切中文；变量名后面紧跟中文被当成变量名的一部分（`$DEST（` 读成一个叫 `DEST（` 的变量），`set -u` 下直接退出 | 脚本开头 `export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8`；变量后紧跟中文一律写 `${VAR}` |
| 2 | 死循环，反复弹窗 + 邮件 | 检查脚本按自己所在位置推项目根，结果写到了别的目录，编排脚本找不到就「继续」重跑 | 检查脚本按当前目录定根；结果文件缺失只自动重试一次，第二次停下一直等人 |
| 3 | 执行模型跑全量测试，流水线白等 | 早期规则要求执行模型收尾前自己跑全量，流水线随后又跑一遍 | 全量交给流水线跑一次，执行模型只跑相关的；返工按波及面表补跑 |
| 4 | 执行模型跳过真实模型调用，检索效果上不去 | 规则里写了「不花钱」，模型就把向量化省掉了 | 费用授权写进提示词：「手册要求的真实调用费用已批准，该跑就跑」；验收提示词：「因省钱跳过的判返工」 |
| 5 | 后台服务关不掉，端口被孤儿进程占住 | 后台进程收不到 Ctrl+C；只杀儿子不杀孙子 | 杀整棵进程树，再按端口清本项目的孤儿；别人的进程不碰 |
| 6 | 推荐是「通过（前提是…）」，点「按推荐办」后静默死循环 | 推荐文本不可机械执行 | 只取推荐开头的指令词；取不出就发邮件说明并继续等 |
| 7 | 代提交从未成功，两线从未同步主干 | `git add` 用排除语法时退出码 1，被 `|| true` 吞掉 | 已忽略目录不再排除；合并没开始要判失败并通知，不静默当成功 |
| 8 | 并入主干后全量测试起不来 | 新段带了新依赖，主干虚拟环境没装 | 并入后依赖清单变了就自动装；记住虚拟环境是哪个工具建的 |
| 9 | AI 产品经理被反复打扰 | 每次「需决定」都等人答 | 红线之外 10 分钟自动按推荐；同一原因第二次才停下 |
| 10 | 验收越做越重 | 每段都写网页自动点击检查、重跑前序阶段 | 验收减负：程序只跑全量测试 + 本段冒烟；验收员并排看 2 到 3 件，15 次工具调用 |
| 11 | pkill 误杀了 AI 产品经理自己的 Codex 对话 | 用进程名匹配杀模型 | 停止只靠「停止」文件和 pid 文件 |
| 12 | 改了一行日志，流水线半夜静默停了 | `set -u` 下引用了只在 `FOO=1 cmd` 前缀里赋过值的变量；`bash -n` 和 shellcheck 都查不出 | EXIT 陷阱报警；改完先跑 `run_sh_check.py` 专抓未赋值变量 |
| 13 | 上一轮的结果冒充了本轮 | 检查程序中途失败没写新结果，验收员读到的是上一轮的文件 | 待验收开头先把旧结果挪成 `_prev` |
| 14 | 验收写了「通过」，冒烟其实是 FAIL | 验收模型读交付说明读得太顺，没对上程序结果 | 程序结果没过，脚本直接改判返工 |
| 15 | 点了「我自己看」，10 分钟后还是自动按推荐了 | 「我自己看」什么都没写，脚本当成没人回应 | 点「我自己看」就往决定文件追加一行暂停，之后不再自动按推荐 |
| 16 | 额度用完，流水线一遍遍白跑 | 额度用完被当成普通异常退出，自动「继续」后再撞一次 | 认出额度用完的字样就一直等人 |
| 17 | 网络抖一下，返工轮次就用掉一轮 | 超时、429 被当成程序错，计入失败次数 | 失败的冒烟步全是连接类错误就判服务故障：不叫验收、不计数、原样重跑 |
| 18 | 执行模型往提示词里堆禁令补丁，成品没变好 | 成品质量问题被写进返工单交给了执行模型 | 先分诊：成品质量进调优清单，由人或方案模型改 |
| 19 | 子段 S2a 找不到共用手册 S2_*.md，一直等手册（自测抓到，没上线） | `${1%%[a-z]*}` 在 UTF-8 区域设置下 `[a-z]` 也匹配大写，段名被整个删掉 | 改用 `[[:lower:]]`；e2e 场景八专测 |

一条总教训：**流程增加人的操作而不提升成品，就是自嗨。** 每加一个确认点、一个审核环节前，先问「这一步让成品更好，还是只让流程更长」。

## 15. 进阶：两线并行（可选，第一版不要做）

真实项目在第 1 段通过后开了两条线，各在自己的 git worktree（`../项目_甲线`、`../项目_乙线`）里，各用自己的服务端口，每段通过就并回主干，开新段前先把主干并进来，最后一段回主干单线收尾。

值得知道的要点：
- 进度表只有主干一份（`STATE_FILE` 指向主干），两线都读写它；副本里那份只是执行模型顺手改的，以主干为准。
- 主干仓库和共用端口要加锁（`mkdir` 原子锁 + pid 文件，持锁进程死了自动清）。
- 合并冲突分两层：能机械处理的（进度表整文件取一边、迁移 HEAD 行取一边）脚本自己做；剩下的交给验收模型解决，解不干净就 `git merge --abort` 等人。合并失败属于一直等人的那类。
- 数据库迁移会出现两个 head，并入时要自动写合并迁移并更新版本号。
- 并入后依赖清单变了要装进主干环境；模型解决过冲突的合并要在主干跑一次全量测试。
- 跨线依赖（前端某段要等后端某段通过）由脚本等着，只写日志不通知，不算故障。
- 每条线一份决定文件，值守按文件分别起草；手册更新在主干，副本到新段开工时才同步过去。
- 重启要挑两线都空的时候：一个进程管两线，重启会打断另一条线正在跑的测试和验收。判断旧进程退没退看日志里的「收到停止」，不要按进程名数，会数到子进程。

代价：编排脚本翻倍，上面第 7、8 条事故都来自并行。**建议先单线跑通一个项目，确认验收标准稳定了再考虑并行。**

## 16. DIY 替换表

| 想换什么 | 改哪里 | 注意 |
| --- | --- | --- |
| 执行模型换成 Claude（Opus 开发） | `run_codex` 换成 `claude -p --permission-mode bypassPermissions`；验收换成 `codex exec` | 保住「执行与验收不同模型」。Claude 套餐额度要先估 |
| 执行模型换成别的 CLI（Gemini CLI、aider 等） | `run_codex` 一个函数 | 要求：能从 stdin 或参数接提示词、无人值守不提问、退出码可读 |
| 验收模型换成 GPT | `run_claude` 一个函数 | 提示词不用改；结论文件格式不变 |
| 值守用的模型 | `DUTY_CLAUDE`、`DUTY_LEAD_MODEL`、`DUTY_PLAN_MODEL` | 默认验收模型 Opus、方案模型 Fable |
| 通知换成 Slack / 飞书 / 企业微信 | `.env` 加 `NOTIFY_WEBHOOK`、`NOTIFY_WEBHOOK_KIND` | 不改代码 |
| 通知换成短信、Telegram 等 | `notify.py` 加一个函数，挂进 `(popup, mail, webhook)` 元组 | 失败要吞掉，不能把流水线搞死 |
| 不是 Python 项目 | `TEST_CMD` 环境变量或 `checks.sh` 的测试命令 | 结果文件结构不变：`{"stage", "items", "numbers"}` |
| 不是代码项目（写作、数据处理、文档） | `checks.sh` 改成格式校验、字数、必含章节等能量的检查；冒烟改成「真实跑一遍产出一件成品」 | 有回归集就让 `scripts/regress.py` 写成品清单，验收会并排看 |
| 什么算服务故障 | `OUTAGE_PATTERN` | 默认认超时、连不上、429、5xx、TLS |
| 什么算额度用完 | `QUOTA_PATTERN` | 默认认 limit / quota 字样 |
| 偶发放行管哪些项 | `FLAKY_PREFIXES` | 默认只放回归件，设空就不放行 |
| Linux 服务器 | 去掉 `caffeinate`；弹窗自动跳过 | 决定靠邮件 + 决定文件；想要弹窗可在 `ask_dialog` 里换 `notify-send` |
| Windows | 用 WSL 跑 | 不要用 Git Bash，heredoc 和中文路径容易出问题 |
| 不用 Git | 什么都不用改 | `commit_all` 检测到不是仓库就跳过。但强烈建议用 Git，返工时能看 diff |
| 子阶段编号不想用 S | 环境变量 `STAGE_PREFIX` | 手册文件名前缀同步改 |
| 更严的审核 | 不建议 | 真实经验：越重越假。先把通过线写得可量，再谈加环节 |
| 更快的节奏 | `MAX_REWORK=2`、`AUTO_WAIT=300`、`POLL=10` | 返工早点交人；5 分钟自动按推荐；等人时 10 秒看一次决定文件 |

## 17. 复刻清单（照着做，约一小时）

**准备（15 分钟）**
1. 装 Codex CLI 并登录；终端跑 `codex exec -m gpt-6-astra "说 ok"` 能出结果。
2. 装 Claude Code 并登录；终端跑 `claude -p --model claude-opus-5-5 "说 ok"` 能出结果。
3. 项目根执行一行安装（`curl … | bash`，要全套加 `-s -- --full`）。
4. 项目根建 `.env`（照 `.env.example`），确认在 `.gitignore` 里。

**定方案（30 分钟，和 Fable 对话）**
5. 让 Fable 读你的需求，把工作切成 3 到 10 段，每段写一份 `手册/Sn_xxx.md`（照 `手册/_模板_Sn_子阶段名.md` 的章节）。切段原则：每段有自己能量出来的通过线。不必一次写完，流水线会等手册。
6. 把段落填进 `项目状态.md` 的进度表。决策台账里写清红线。

**接检查（10 分钟）**
7. 改 `pipeline/checks.sh`：测试命令换成你的（或设 `TEST_CMD`）；冒烟约定不变。
8. 手跑一遍：`bash pipeline/checks.sh S1`，看 `运行数据/pipeline/accept_S1.json` 生成了。
9. 测通知：`python3 pipeline/notify.py 测试 正文`，手机收到邮件。

**启动（5 分钟）**
10. 项目根执行第 13 节的启动命令；装了全套就把值守也起上。
11. 看 `tail -f 运行数据/pipeline/日志/pipeline.log`，第一段开工就可以走开了。

**第一段通过后再做**
12. 读第一份验收结论，看通过线是不是真的可量；不可量就让 Fable 改手册，不要改验收提示词放宽。
13. 有「调优清单」就改提示词或模板，改在最宽的一层。
14. 看执行模型最后回复（`Sn_dev_last.txt`）有没有「需 AI 产品经理决定」，有就进决策台账。

## 18. 费用与额度

- **方案模型**：主要在对话里用，一个 10 段项目大约 5 到 10 次深度对话（写手册、几次裁决、改流程）。装了值守后，第 4 级返工、夜里的决定、审稿包也会起它的短会话，每次只读文件、写结果。这是最贵也最值的部分，不要省。
- **执行模型**：Codex 按订阅算。
- **验收模型**：每段一次 `claude -p` 加上返工轮次，走订阅额度，占用很小；值守的出事处理和级别 1 返工起草也用它。
- **产品自身的模型调用**（冒烟、评测里的真实调用）：另算，由 AI 产品经理在决策台账里批准。**这条授权和工具用量是两回事，不要混用。**
- **通知**：零成本。
- 不要把「工具额度已批」理解成「可以新开付费服务」。新开任何付费的东西都走红线。
